# 模型调研与评测SOP讨论

状态：讨论已收敛，用户已整体确认[统一SOP](model-evaluation-sop.md)。本页保留决策与调查依据。日期：2026-10-21（Asia/Shanghai）。

## 用户提出的方向

先了解目标设备、资源和可用加速条件，再调研模型、框架、后端及量化等候选。针对任务固定指标、输入及benchmark方法，先独立测各模块并比较，再考虑多个进程同场运行的退化。保存结构化结果，由静态HTML模板展示；当前历史材料需要按统一方法整理。

## 本轮已确认

- 区分受控后端对照与实际部署方案对照，并分别展示。可兼容的测试案例和代码应尽量复用；无法保持一致的精度、预后处理等条件仍须明确。
- 允许先测性能；进入最终推荐需要质量证据。无独立标注的功能/性能探针不冒充质量验收。
- 针对当前目标默认推荐一套方案；只有适用条件或资源取舍明确不同时，保留少量有价值的备选，其余结果归档。不预先硬分性能/资源档位。
- 先建立通用SOP与结果格式，以ASR完整验证，再扩展到TTS/LLM。
- 历史原始证据保留，先转换可靠字段、缺失项标为未测，再按关键决策缺口补测；不因格式变化全量重跑，也不追认旧实验遵循新协议。
- ASR第一版同时保留非实时吞吐与实时流式两种测试场景，分别展示、尽量共用用例；ROS链路和多模块共跑在后续阶段。
- 执行强度分快速筛选与候选复测两级，数据带版本和比较条件，两级结果不混排。
- 用户进一步明确个人开发者约束：语料小而固定，适合机器人、有部分参考性即可；首要关注资源占比和性能。不建设大规模语料或新的人工作业流程。
- 优先使用模型随附测试语料或可低成本取得的现成参考转写，再补少量机器人业务样本；来源与标签可信度分开记录。
- 不将人工末音标注作为首版前置条件。没有人工EOS时保留明确命名的能量代理/文件边界等待，不报告人工末音延迟或误切分准确率。此项取代前一轮“首版补人工末音标注”的建议。
- 初筛每配置1轮，入围配置独立复测3轮；保留逐条结果及中位数/范围，加载、首请求、预热后结果分开。重复录音不增加独立语料数量。
- 最终推荐所需质量证据按小样本有限范围提供，优先现成参考文本；没有可靠参考的材料只作功能/性能回归，暂列为性能候选，不补造准确率。

## 成熟体系的参考原则

以下为一手资料调研后对本仓库的建议，并非完整采用原体系，也不将本仓库结果称作MLPerf成绩。

| 体系 | 可借鉴的原则 | 适用边界 |
| --- | --- | --- |
| [MLPerf Inference规则](https://github.com/mlcommons/inference_policies/blob/master/inference_rules.adoc) | 定义被测系统、任务、数据、质量条件和负载场景；披露改变的条件 | Closed允许满足规则的量化，并非简单要求所有产物逐比特相同；本仓库的两类对照是自己的归因约定，不等同于MLPerf分区 |
| [MLPerf Tiny规则](https://github.com/mlcommons/tiny/blob/master/benchmark/MLPerfTiny_Rules.adoc) | 固定输入、预后处理、质量及运行计时方法，结果可复现 | Tiny的既定低功耗任务不能直接替代中文语音与本地LLM场景 |
| [HELM原则](https://crfm.stanford.edu/2022/11/17/helm.html) | 统一场景适配，同时报告多个质量和效率指标，明示覆盖缺口 | 不将大规模通用任务清单全量移植到RK3566 |
| [GenAI-Perf文档](https://docs.nvidia.com/deeplearning/triton-inference-server/user-guide/docs/perf_analyzer/genai-perf/README.html) | 区分首响应、总延迟和吞吐；导出JSON/CSV后绘图 | 当前官方已提示新需求转向[AIPerf](https://github.com/ai-dynamo/aiperf)；本次借鉴定义，不决定新增工具依赖 |

## 当前工具审查摘要

已有结构化JSON/JSONL、资产与源码hash、资源时序、单模块/共跑套件及静态HTML数据重建，可继续复用。

主要缺口是：协议和指标定义没有版本；同名计时存在不同scope；执行正常退出和质量/性能达标未分成独立状态；图表主要按相同输入归组，尚未校验完整比较条件。ASR离线吞吐、实时流式和ROS交付，以及TTS纯generate和WAV就绪不宜自动混排。

历史证据应保留；能可靠映射的字段可进入新视图。人工转写/EOS、真实首声、长期统计及NPU独立内存等未测内容不能补造。实施方式现已按SOP确认，见结果格式与ASR试点。

## ASR试点：讨论时核对的事实

- 现有fixture清单有`schema_version: 1`，这是素材清单版本；通用suite/result/metric协议尚无统一版本，二者应区分。
- 四个现有固定素材仅有能量起止参考；命令参考来自先前ASR一致输出，官方素材无独立转写；不能直接作为正式CER或人工末音延迟的标签。
- 常驻C API探针和worker可配置CPU/provider，但现有冻结常驻实验全为NPU；同适配器CPU常驻对照仍需实测。已有CPU Python/CLI结果不能假称该项已完成。

## ASR语料调研（讨论时的备选）

公开集可考虑[FLEURS普通话](https://huggingface.co/datasets/google/fleurs/blob/main/README.md)，已有参考转写、16kHz音频及测试划分；[AISHELL-1](https://www.openslr.org/33/)也有人工转写，但官方总包约15GB，如已有缓存可优先复用。先固定子集，报告只代表该子集；公开朗读成绩不代替机器人远场与指令质量。

两种标准资源均不能直接提供本轮所需的人工末音参考；文件长度、能量末端和强制对齐时刻应各自标明来源。现有本地四素材及拼接六轮可以继续作性能/流程回归，但不是独立语料数量或独立质量标签。上述为讨论时状态；实施后以ASR v1实验记录为准。

## 资源采样核查

现有工具约200ms采集进程树CPU核秒、PSS/RSS/Swap及主机可用内存，并记录温度/CPU和NPU频率。CPU占整机容量可由核秒、窗口墙钟和逻辑CPU数推导；历史未统一冻结MemTotal分母，不能直接用标称4GB回填精确内存占比。

加载、常驻待机与推理窗口尚无统一可对齐的阶段边界；下一版需补充阶段时间标记和固定短待机窗口。当前没有NPU忙碌率、独占内存或功耗读数；频率不是利用率，PSS不是NPU专用内存。

## 实施后用户纠正：主对照必须先统一精度

用户指出CPU/NPU比较应先统一精度。此前虽将CPU混合int8与NPU浮点标为部署方案对照，但把它作为首个主基线并给出NPU默认推荐，执行顺序和结论不充分。已撤回推荐，SOP更新为先建立同源、同精度及相同输入/流式配置的受控主对照，再展示实际部署取舍。

本机现有CPU资产只有混合int8 ONNX与FP32 decoder；已验证NPU资产为另行导出的RKNN浮点版本。暂无已验证的匹配精度组合。下一步需核对CPU FP16实际算子支持/升精度或NPU INT8导出可行性及权重谱系；不能只改provider或模型标签，也不能将CPU FP32对NPU FP16改称统一精度。未完成前保留缺口，不改写原始数据。

补核依据：[ONNX Runtime官方FP16文档](https://onnxruntime.ai/docs/performance/model-optimizations/float16.html)说明了不支持算子的FP32保留与Cast，并提示CPU版FP16支持限制；这表明不能假定“将文件转为FP16”就等于CPU全程FP16执行。本机SDK的实际能力仍需单独核验，尚未声称FP16 CPU ASR已跑通或一定不可行。
