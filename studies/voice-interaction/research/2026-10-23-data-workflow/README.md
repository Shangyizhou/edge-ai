# 数据准备顺序与 Train / Benchmark 交接调研

日期：2026-10-23。状态：建议，未修改 Skill 或执行数据生成、训练、模型测试。承接[部署 Skill 边界调研](../2026-10-23-deployment-skill-boundaries/README.md)。本页综合官方工具文档与本地现有契约，设计建议不是某一框架规定的行业标准。

## 结论

接受用户提出的“独立、可审阅、可复用的数据阶段”，但不新增 Data Agent / Skill。增加 Train 的数据准备模式和 Benchmark 的评测准备模式，在执行语义上分开；具体 CLI 名称和 JSON schema 尚未实现。Prepare 继续只负责推理/测评就绪。

任务与评分规则应先于大量制作训练样本；对来源与近重复样本先分组划分，再扩写训练集。数据准备、运行环境准备可以并行，完整数据准备不依赖板端先跑通；模型相关分词/模板预检则需要选定 tokenizer/template 和可运行的相关工具。

## 一手资料及其适用范围

1. scikit-learn 的常见问题说明：测试集不参与模型选择，依赖数据学习的变换只在训练子集拟合，再应用到其他子集。此处不能机械推导为“划分前连损坏文件和重复都不许检查”。[数据泄漏说明](https://scikit-learn.org/stable/common_pitfalls.html)
2. GroupShuffleSplit 支持按组划分，比例是按组而非严格按样本行数。我们的来源/模板族/会话分组需要自行定义；随机种子只保证可复现，不自动防泄漏。[分组划分](https://scikit-learn.org/stable/modules/generated/sklearn.model_selection.GroupShuffleSplit.html)
3. AWS 提倡区分 train、validation、test，并提醒重复样本与分层覆盖。其比例是示例，不是所有端侧任务的规范。[数据划分](https://docs.aws.amazon.com/prescriptive-guidance/latest/ml-operations-planning/splits-leakage.html)
4. MLX-LM 文档支持 JSONL 和工具消息；valid 用于训练验证，--test 用于测试困惑度。工具参数可随模型使用字符串或对象，文档要求参照对应模型。不能把它的 test 文件名等同于原生工具任务验收。[MLX-LM LoRA / Data](https://github.com/ml-explore/mlx-lm/blob/main/mlx_lm/LORA.md)
5. TRL 的工具训练格式包含 messages 与 tools，工具调用示例使用结构化 arguments。说明对话语义数据和最终模板序列应分层；不要求我们改用 TRL。[工具数据格式](https://huggingface.co/docs/trl/dataset_formats#tool-calling)
6. Hugging Face 数据卡及元数据支持描述来源、标注产生方式、语言、许可等。我们可用本地数据说明与清单承载，不要求上传 Hub。[数据卡](https://huggingface.co/docs/hub/datasets-cards)、[元数据字段](https://huggingface.co/docs/huggingface_hub/en/package_reference/cards)
7. Google Research 的去重研究及代码提供精确与近重复方法，说明去重不仅是节约计算，也影响记忆和评价。此处只借鉴，不建议为几百条指令引入整套大语料工具。[去重项目](https://github.com/google-research/deduplicate-text-datasets)
8. Distilabel 提供生成和 AI 反馈流水线，可以作为未来规模化参考。当前无需新装此依赖；AI 生成/评价仍不等于业务真值。仓库注明维护现状，不能因存在框架就假定适合立即采用。[Distilabel](https://github.com/argilla-io/distilabel)

## 推荐顺序

| 阶段 | 责任与工作 | 可审阅交付 |
| --- | --- | --- |
| 1. 定义任务 | Selection / Ask 承接用户目标；Benchmark 细化评分；Train 说明可学习行为 | 任务范围、工具/事实版本、成功/澄清/无调用规则、门槛来源 |
| 2. 采集种子 | Train 制作学习材料；Benchmark 制作评测材料，记录真实/人工/合成来源 | 原始材料目录、来源与标注规范、覆盖矩阵 |
| 3. 初步整理与分组 | 检查损坏/格式问题、精确去重、识别相同来源/模板派生/近重复族 | 分组映射、冲突与排除理由 |
| 4. 分配用途并隔离 | 分配 train、validation、诊断/回归、最终 holdout；按任务类别检查覆盖 | 划分映射、随机种子/规则、样本与组数、初步交叉检查 |
| 5. 制作与扩充 | Train 只在允许的学习来源扩写、清洗和标注；Benchmark 独立制作评测答案 | 父子来源关系、生成模型/提示词版本、标注与复核记录 |
| 6. 导出与预检 | Train 导出框架兼容格式；Benchmark 导出 suite 与评分配置 | schema 结果、实际 token 长度、mask/结束标记证明、评分器小样例自检 |
| 7. 复核并冻结 | 复查跨集合重复、覆盖和标签；版本化清单与批准状态 | 冻结数据版本、哈希、数据说明和只读报告 |
| 8. 实验 | 基础模型诊断评测；有必要才训练；验证选定候选后最终独立测评 | 带版本的结果；失败保留；不自动把所有结果回流训练 |

这不是要求标注前不能划分。任务标签可先做以便分层，或者先按来源预留，再分别精标；关键是不得先生成一大批互相关联的改写，再随机拆行假装独立。

最终 holdout 的原始来源也应预留在训练开发之外。清单冻结前做质量复核；冻结后如发现标注缺陷，按独立、可追溯的更正流程建立新版本，所有对比候选重新评分，不按某个模型的输出来修改答案。

## 数据集用途与结果回流

| 用途 | 可以用于什么 | 不应怎样宣传 |
| --- | --- | --- |
| Train | 梯度更新 | 训练成功不代表泛化 |
| Validation | 选参数、检查点、adapter；训练 loss 和任务验证 | 参与选配后不能称最终独立结果 |
| 诊断/回归 | 查看失败、改 prompt 和数据、追踪已知缺陷 | 未参与梯度也不自动算未见最终集 |
| Final holdout | 预先确定的候选、配置和评分规则下做版本验收 | 持续根据具体错误调参后，不能重复称其为未见测试 |

这是四种逻辑用途，不强制每次四个不同文件。小试点可将 validation 与开发诊断结合并如实注明；不再额外维护一套几乎相同的集合。可调用 Benchmark 对 validation 做任务评分，但结果用途仍是 validation。

同一冻结最终集可以用于预先选定的基础/微调/量化候选配对比较；候选和配置应在看最终结果前确定。若用最终分数挑量化精度或 prompt，就要承认该集参与选择。先在诊断集比较基础模型，再决定是否训练；不必先制作完整训练集。

评测后可以展示最终失败用于透明审阅；一旦开发者据此改动，就记录它已进入开发反馈，未来重要验收需另设新的未见数据。已有 Qwen 最终132例已被详细讨论，适合作为历史/回归，不能重命名后重新声称未见。

## Qwen 工具调用的具体要求

- 用户给出的 move_forward/distance 示例仅为假设；实际工具名、单位、类型、约束取自 ros-robot 当前 Registry / Schema。不能将假设接口直接混入本轮数据。
- 训练与推理需匹配官方 tokenizer/chat template。业务层预期行为、训练结构、模型输出标记和 Agent 接收对象是不同层次；不要把普通 content 的自定义 tool/arguments JSON 当成原生调用训练目标。
- 建议内部语义记录保留 arguments 对象，框架适配层按实际模板要求转换，检查反斜杠/引号等复制边界，避免双重 JSON 编码。公开示例的 arguments 字符串不能直接决定当前 Qwen 适配器格式。
- tools、必要 system、当前上下文属于输入；事实人设必须来自明确来源。动态状态不能被伪装成固定事实。
- 格式/schema 自动检查与意图/参数正确分开；Schema 合法不证明标签语义正确。无默认值的模糊指令应依据已定策略澄清，不能自行编数值。
- 单调用、多调用、不开工具、澄清、人设事实和参数边界应分别报告覆盖，不能仅堆叠近义句增加总数。
- 来源组不等于工具名。若目标是在已知工具上泛化，同一工具可在各集合出现，但同一来源和模板派生族不跨集合；若要测试新工具泛化，应另设明确的工具留出实验。
- 训练预检渲染完整 tools+system+对话+目标序列，核对长度和实际监督 mask，不静默截断。当前已安装 Train 已含相应原则；需补的是可独立停止的数据准备交付。

## Train 与 Benchmark 的责任，不新增 Skill

Train — 数据准备模式：接收任务、允许使用的来源和分组划分规范；收集/导入、清洗、生成、标注、质量检查和框架导出，只交付 train/validation、统计与溯源，可在这里停止。Train 的训练执行模式只消费已冻结的数据版本，不边训练边无记录改数据。

Benchmark — 评测准备模式：定义/导入诊断与最终评测材料、评分器、版本和审阅记录；参与分组隔离检查。随后执行模式消费冻结 suite。它可以由模型辅助制作，但不使用被测模型自己的回答直接当真值。LLM reviewer 需记录模型/版本/提示词与复核；固定规则评分优先用于可确定的工具参数。

Prepare：检查模型、运行框架、实际后端和最小推理，解析测试配置指向的输入与工具是否存在；不拥有标签/划分/评分政策。可在数据准备前后或并行进行，不设为数据制作前置条件。

Ask：汇总现有证据和任务优先级，建议先诊断、补数据还是停止，不自动训练。

这是对入口和文档的建议，不是已安装的新 CLI 或 schema。

## 交付包：少量权威记录与派生文件

建议一份数据清单、一份样本/分组映射、一份评分配置，加上各用途的数据与质量记录；同一工具 schema 和任务定义用引用而非多份手抄。原始/派生关系、用途、标签、合成方法、审阅、排除理由、样本/组数量和哈希可追踪。文件后缀 YAML/JSON 不决定职责，优先沿用项目已有 JSON。

最终测试内容与训练导出路径分开；Train 默认仅获得开发数据和最终集的版本/覆盖概况，不读取最终题目答案来生成训练资料。需要去重审计时由评测检查器执行，记录范围；不要把最终案例全文回传到训练提示中。

“Benchmark 保管”只是职责和访问约定。相同代理上下文、共享目录并不提供真实保密；若验收确需盲测，必须用隔离执行环境/访问控制或独立保管人。当前不建立新的权限系统，也不能据文件夹分开就宣称盲测。

人工/真实数据与 AI 生成无需二选一。建议真实表达和人工确认规范作为种子，AI 做训练侧改写/组合及初标，程序校验后抽查语义；最终评测标签独立复核。新任务先少量验证规则与格式，再按覆盖缺口扩展，不固定1000条或70/15/15比例，不立即引入 Distilabel/Argilla 等依赖。

## 数据审阅 HTML 建议

沿用已认可的左导航、单环节、上一/下一环节交互，作为 Train/Benchmark 的数据准备视图，不新增报告 Skill：

1. 要学/测什么：行为规范、来源和未知项。
2. 数据从哪里来：真实/人工/合成构成、分类/组数、标注方式。
3. 怎样划分与检查：重复/泄漏检查、覆盖缺口、格式与 token 预算。
4. 审阅与冻结：少量各类代表案例、未决标签、数据版本和下一步；允许准备完停止。

训练曲线属于后面的训练环节，数据审阅时不得显示尚未发生的 loss。为保护最终集，训练侧主报告只显示其统计/版本，最终具体案例由授权评测视图控制。详细记录与所有数据仍放独立索引，不挤进主报告。

## 当前缺口与最小下一步

当前 Train / Benchmark 合同已包含来源组、数据哈希、模板预检和冻结 suite，但没有完整的数据准备入口、通用数据清单/跨集合审计交接与对应页面。本轮不宣称已实现。

建议只读映射已有 Qwen 数据到上述逻辑结构，标出哪些集合已参与选配、哪些最终例已观察，绝不重写历史样本/分组；用少量明确标为假设的数据演示下一轮分组与两种数据视图，再决定是否将入口写入 Skill。完成审阅前不生成新训练集、不启用新权限、不开始模型执行。
